# Flutter Application Architecture - JustUS

## Overview

JustUS is a private couples app ("Just Us") built with Flutter. The Flutter application lives in `Flutter/` and follows a **feature-first layered architecture**:

- `lib/core/` - cross-cutting infrastructure: networking, local storage, realtime, notifications, error handling, versioning, localization, theming, media.
- `lib/features/<feature>/` - each business capability (auth, partnership, home, mood, games, bucket_list, drive, settings) split into `models/`, `repository/`, `state/`, `screens/`, `widgets/`.
- `lib/shared/` - reusable design system (`shared/design_system/`), generic utilities (`shared/utils/`), generic widgets (`shared/widgets/`).
- `lib/all_imports.dart` - auto-generated single import barrel (regenerated by a pre-commit hook). Nearly every file imports only this barrel, which creates a single-file circular import graph (see Findings).

State management is `provider` + `ChangeNotifier`. All feature states extend `BaseState` (a `ChangeNotifier` with frame-coalesced notifications). All repositories extend `BaseRepository`, giving uniform access to Supabase, checkpoint-based change detection and the backend `ApiService`.

The app uses two trust paths:

1. **Flutter -> Supabase (direct)** for RLS-safe data operations (moods, missyou, bucket list, game answers, drive dashboard via views, partnership RPCs). Configured in `lib/core/network/supabase_service.dart`, called through `BaseRepository.sbClient`.
2. **Flutter -> Node/Express backend (`/api/v1`)** for privileged operations that are abusable/billable: AI question generation, Cloudflare R2 media presign/complete, FCM device-token registration, session binding sync, invite, login-risk check, refresh proxy, user wipe. Driven by `lib/core/network/api_service.dart` (HMAC-signed, nonce-protected, JWT-authenticated).

The Flutter app is NOT responsible for the database schema; it relies on hosted Supabase objects (`v_active_partnership`, `v_drive_dashboard`, RPCs `request_partnership`/`accept_partnership`/`send_missyou`/`set_mood`, etc.) that are documented in `.agents/skills/` but are not versioned in the repo.

## Entry Point & Bootstrap Sequence

Entry: `Flutter/lib/main.dart`.

`main()` runs inside `runZonedGuarded(...)` (zone errors land in `ErrorHandler.handleGlobal`) and is invoked with `unawaited(...)`:

1. `WidgetsFlutterBinding.ensureInitialized()`.
2. `FlutterError.onError` is overridden -> `FlutterError.presentError` + `ErrorHandler.handleGlobal`.
3. `await dotenv.load()` - loads `.env` (required for Supabase URL/anon key and Turnstile key). **Hard prerequisite, blocking, throws if absent.**
4. `await StorageService.init()` - initializes the `SharedPreferences` singleton.
5. `await SupabaseService.initialize()` - reads `SUPABASE_URL`/`SUPABASE_ANON_KEY` from dotenv, throws `Exception('Supabase configuration missing in .env file')` if empty, then `Supabase.initialize(url, publishableKey, httpClient: LoggingHttpClient)`.
6. On Android/iOS/Web: `await Firebase.initializeApp` (wrapped in try/catch, failure only logged), registers `FirebaseMessaging.onBackgroundMessage(_firebaseMessagingBackgroundHandler)`, grabs `FirebaseAnalytics.instance`.
7. `final notificationService = NotificationService(); await notificationService.init();` - local notifications, permissions, foreground handler (see Notifications Initialization).
8. `final languageProvider = LanguageProvider(); await languageProvider.loadSavedLocale();` - reads persisted locale before first frame.
9. `runApp(JustUsApp(languageProvider, analytics))`.

**Characteristics**

- Steps are strictly **sequential** (each `await` gates the next). No parallel warm-up of independent subsystems except the `Future.wait` inside `AuthState.init()`.
- Steps 1-8 all run **before the first frame**. Any throw in steps 3-5 aborts startup entirely and is only reported through `handleGlobal` (no user-facing retry UI); the Flutter engine shows a blank/error state.
- Firebase init is the only step with a local fallback (catch + log).
- There is **no dependency injection container**: providers, repositories and services are instantiated with `new`/`?? Default()` at fixed call sites. Testability relies on constructor injection in states/repositories, but default constructors are used everywhere in production.

`JustUsApp` (StatelessWidget) builds:

```
MultiProvider(
  ChangeNotifierProvider.value(LanguageProvider)          // pre-loaded
  ChangeNotifierProvider(AuthState)
  ChangeNotifierProvider(PartnerState)
  ChangeNotifierProvider(ThemeProvider)
  ChangeNotifierProvider(HomepageState)
  ChangeNotifierProvider(MoodState)
  ChangeNotifierProvider(BucketState)
  ChangeNotifierProvider(GameState)
  ChangeNotifierProvider(DriveState)
  ChangeNotifierProvider(ProfileState)
  child: RealtimeSyncScope(
    child: Selector2<LanguageProvider, ThemeProvider, _AppThemeData>(
      MaterialApp(
        navigatorKey: ErrorHandler.navigatorKey,
        navigatorObservers: [FirebaseAnalyticsObserver?],
        themeMode / locale / supportedLocales / localizationsDelegates,
        theme: AppTheme.light, darkTheme: AppTheme.dark,
        home: SplashScreen(),
        routes: {/login, /register, /homepage, /partner, /localization, /change-password},
      )))
)
```

All eleven providers are created **eagerly at startup**, regardless of which screen/tab the user will reach. Each feature state immediately builds its repositories (defaults -> own `ApiService`/`http.Client`).

## Startup Lifecycle (SplashScreen -> destination)

`lib/features/auth/screens/splash_screen.dart`:

- `initState()` -> `unawaited(_checkAuth())`.
- `_checkAuth()`:
  1. `await authState.init()` - full session bootstrap (see Session Initialization).
  2. If `authState.isLoggedIn` -> `await partnerState.fetchPartnership()`.
  3. Routing (all `Navigator.pushReplacement` with inline `MaterialPageRoute`, NOT the named routes):
     - logged in + partner present -> `MainShell(key: MainShell.shellKey)`.
     - logged in + no partner -> `PartnerScreen`.
     - not logged in -> `LoginScreen`.

`LoginScreen` (`lib/features/auth/screens/login_screen.dart`) performs its own session bootstrap after a successful `AuthState.login(...)` and navigates to `MainShell`/`PartnerScreen` accordingly (same decision: `AuthState.hasPartner`).

`RegisterScreen` (`lib/features/auth/screens/register_screen.dart`): on success, if already logged in (auto-confirmed account) -> `pushAndRemoveUntil(PartnerScreen)`; else shows a "confirm your email" dialog and returns to Login.

### What blocks navigation

- `AuthState.init()` and `PartnerState.fetchPartnership()` are awaited by the splash; navigation cannot happen until both complete.
- Inside `init()`, several **backend network calls are awaited**: session sync (`/auth/session-sync` -> binding secret) and FCM device-token registration. Their failures are **caught and only logged** - they do not block navigation - but there is a hidden consequence: if session-sync fails, no binding secret is saved and later signed requests (device-token, media, AI) fail as `NetworkError`.
- `PartnerState.fetchPartnership()` uses `runSafe()` (`showLoading: true`); a network failure is routed through `ErrorHandler` (snackbar/dialog) and leaves `partner == null`, so the splash navigates to `PartnerScreen` even when a partnership actually exists in the DB.

### Failure behavior

- If `AuthState.init()` itself throws (e.g. storage read error, or `logout()` triggered mid-init), the exception propagates into `_checkAuth`, which has **no try/catch**. Because the future is `unawaited`, the error surfaces to the zone -> `runZonedGuarded` -> `handleGlobal` -> post-frame overlay. The splash spinner can remain on screen.
- `handleGlobal` defers UI to a post-frame callback specifically because it is invoked from build/error phases (see Error Handling).

### Can initialization run more than once?

- `main()` bootstrap: once per process.
- `AuthState.init()`: designed to be re-runnable - it first cancels the previous auth/token subscriptions and re-reads storage. In practice it is invoked once per cold start (from `SplashScreen`); `login()`/`logout()` do NOT call it.
- `RealtimeSyncService.start()` is guarded by `_started`; `configure()` re-runs on auth/partner changes.

### Provider registration (`lib/main.dart`)

| Provider | Class | Base |
|---|---|---|
| LanguageProvider | `ChangeNotifierProvider.value` (pre-loaded) | ChangeNotifier |
| AuthState | global session/user/partner/invitations | BaseState + WidgetsBindingObserver |
| PartnerState | partnership search + requests | BaseState |
| ThemeProvider | dark/light mode | ChangeNotifier |
| HomepageState | miss-you counter | BaseState |
| MoodState | moods | BaseState |
| BucketState | bucket list | BaseState |
| GameState | couple game | BaseState |
| DriveState | shared drive | BaseState |
| ProfileState | own/partner profile | BaseState |

### BaseState (`lib/shared/utils/state/base_state.dart`)

- `notifyListeners()` is **coalesced per frame**: only one real notification at the end of the frame (`addPostFrameCallback`), preventing rebuild storms during multi-provider startup.
- `runSafe(action, {showLoading})`: sets loading, clears message, awaits, on error -> `ErrorHandler.handle(e)`, returns bool success. **The universal error boundary for user actions.**
- `handleResult<T>(result, {onSuccess, notifyOnSuccess})`: pattern-matches `Success/GenericError/NetworkError`; non-success paths go through `ErrorHandler` and call `notifyListeners()`.
- `loadWithChangeDetection({loadFromCache, hasChanges, fetchFromNetwork})`: cache -> checkpoint diff -> fire-and-forget network refresh (`unawaited`, not awaited - UI renders cache immediately).

### State-scoped observations

- `AuthState.login()` runs a full 5-step sequence (risk check -> captcha -> Supabase sign-in -> profile fetch -> persist login data -> session sync -> device-token registration -> partner fetch). Partner fetch failure is swallowed with an empty `catch (_) {}` (auth_state.dart, "Step 5").
- `AuthState.register()` performs only signup; it **does not** set login data even when Supabase auto-confirms (so no session bootstrap happens on register).
- `PartnerState` debounces the email search (300 ms) and re-fetches partnership on realtime events.
- `ProfileState.loadProfile()` has a 1-minute throttle (`_fetchThrottle`) and an `isLoading` guard that **silently skips** the whole load (including the cache path) if a load is already in progress.

## Service & Repository Layer

### BaseRepository (`lib/core/network/base_repository.dart`)

- `sbClient` -> `SupabaseService().client` (the singleton Supabase client) unless overridden by constructor `sbClient` (used by tests).
- `getUserId()` -> from secure storage.
- **Server-side change detection**: `fetchMaxTimestamp(table, field)` queries `max(field)` with in-flight dedup (`_pendingTimestampFetches`); `hasChanges(...)` compares checkpoint vs server max timestamp, supporting `kCheckpointEmpty` semantics (server returned no rows -> cache is stale only if the checkpoint says data existed).
- `withUser` / `withPartnership` / `withCouple` helpers that resolve the current user/partner and wrap errors in `ResultWrapper`.
- `getActivePartnership()` -> `PartnershipRepository.getActivePartnership()` (view `v_active_partnership`).
- `notifyPartnerOnce(...)` -> **creates a transient `ApiService`** (new `http.Client`) for fire-and-forget FCM notifications; all errors are swallowed except logging.

### Feature repositories

Every feature exposes `*Repository extends BaseRepository`:

- `AuthRepository` - `checkLoginRisk`, `reportFailedLogin`, `syncSession` (all via backend API), `currentSession`, `signInWithPassword`, `signUp`, `signOut`, `changePassword`, `updateDeviceToken` (backend, signed).
- `PartnershipRepository` - `getActivePartnership()` (with a **static shared future cache** keyed by user; invalidated via `clearPartnershipCache()`), `getPartnership()`, `fetchPartnerProfile()`, `searchPartner` (Supabase, `ilike`), `sendPartnerRequest` (backend `/auth/invite`), `acceptPartnerRequest` (RPC `accept_partnership` + fire-and-forget `requestAccepted` notification), `rejectPartnerRequest` (direct `partnerships` delete), `updateAnniversaryDate`, `getPendingInvitations` (Supabase query with joined users/profiles).
- `MissYouRepository`, `MoodRepository`, `BucketRepository`, `GameRepository`, `DriveRepository`, `UserRepository`, `VersionRepository` - feature data access (Supabase views/RPCs) plus backend calls for media/AI where needed.

### Services

- `ApiService` - see Network Layer.
- `SupabaseService` (`lib/core/network/supabase_service.dart`) - lazy singleton holder; `initialize()` must be called before first use (hidden init requirement, satisfied in `main()`).
- `NotificationService` - singleton FCM/local notifications.
- `RealtimeSyncService` - see Realtime Initialization.
- `StorageService`, `CacheService` - see Storage & Caching.
- `CaptchaService` - `getCaptchaToken()` runs an **invisible** Cloudflare Turnstile challenge inside a non-dismissible `AlertDialog` using `ErrorHandler.navigatorKey.currentContext` as the host context. Throws `AppError(apiValidation001)` if `TURNSTILE_PUB_SITE_KEY` missing.
- `DeviceTokenService` - `supportsFcm` = Android/iOS/Web; desktop fallback = persistent UUID fingerprint. `getDeviceToken()` returns `'UNKNOWN_DEVICE_TOKEN'` if unavailable.
- `UpdateService` - version check + force-update dialog.
- `MediaService`/`CompressionService`/`MediaCacheManager` - upload pipeline and R2 media caching (not part of bootstrap, used on demand).

## Network Layer

### ApiService (`lib/core/network/api_service.dart`)

- Wraps `http.Client` in `LoggingHttpClient` (logs REST/RPC/Auth/Storage requests).
- **Headers**: `Authorization: Bearer <supabase access token>` (from `Supabase.instance.client.auth.currentSession`), `X-Device-Fingerprint` (cached static within the process after first read), `X-Client-User-Agent`, `X-Client-User-Agent-Hash`.
- **HMAC request signing**: for signed endpoints it builds `X-Request-Timestamp`, `X-Request-Nonce` (UUID v4), and `X-Request-Signature` = HMAC-SHA256 over `METHOD.path.timestamp.nonce.bodyHash` using the **session binding secret**. If the binding secret is unavailable and `requireSignature: true`, it throws `HttpException('Missing request binding secret')` - surfaced to callers as `NetworkError` (hidden init requirement, see Findings).
- **Response handling** (`_safeCall`): default timeout 10s (AI question has 60s); 2xx -> decode via `compute()` isolate; 401 -> `_tryRefreshToken()` (backend `/auth/refresh` proxy with the stored refresh token) then a single retry; refresh failure -> `onSessionExpired?.call()` (global callback -> `AuthState.logout()`) and `GenericError(401)`. Non-2xx parses the `{error:{code,message,severity}}` envelope into `AppError`.
- **Static mutable state**: `ApiService.onSessionExpired`, `_cachedDeviceFingerprint`, `_cachedRequestBindingSecret` (see Findings).
- `resolveProtectedMediaUrl(url)` rewrites raw R2 object keys into `GET /api/v1/media/file?filename=...` URLs (used by avatar widgets).
- `authHeaders` static getter - used by `ProtectedNetworkImage` for authenticated image downloads.

### ResultWrapper (`lib/core/network/result_wrapper.dart`)

Sealed: `Success<T>` / `GenericError<T>(code, message, details)` / `NetworkError<T>(message)`. Handled by `BaseState.handleResult`, `ResultWrapperExtensions.handle/handleAsync/map/valueOrNull/isError/isSuccess` (`lib/shared/utils/extensions/result_extensions.dart`).

### Dual token-refresh mechanisms

1. **Supabase client built-in**: `AuthState` listens `auth.onAuthStateChange` -> `tokenRefreshed` -> persists new access/refresh tokens to secure storage.
2. **Backend-proxy manual refresh**: `ApiService._tryRefreshToken()` calls `POST /auth/refresh`, stores tokens, retries the original request.

Both write to the same secure-storage keys (`access_token`, `refresh_token`), so they are complementary but can race. There is no central "token owner"; `ApiService` reads the token from the live Supabase session while `AuthState` maintains its own `_accessToken` copies.

## Storage & Caching

### StorageService (`lib/core/local_storage/storage_service.dart`)

- `SharedPreferences` (initialized in `main()` via `init()`; lazily re-fetched in the async `prefs` getter) - non-secret data plus caches.
- `flutter_secure_storage` - tokens, user id, partner id, partnership id, device fingerprint (UUID v4), request binding secret.
- JSON encode/decode **offloaded to isolates** via `compute()` (top-level isolate helpers).
- On read of `partner_id`/`partnership_id`, `-1` is translated to `null` (legacy sentinel).
- `saveRequestBindingSecret` also updates `ApiService._cachedRequestBindingSecret` (inline bridge across layers).
- `clearAppCache()` clears non-secret data; `clearAll()` + `clearPartner()` for logout.

### CacheService (`lib/core/local_storage/cache_service.dart`)

- Checkpoint keys: `chk_game_answers`, `chk_moods`, `chk_bucket_items`, `chk_drive_items`, `chk_miss_you`; sentinel `EMPTY` for "server has no rows".
- `needsRefresh(key, {60s})` - freshness gate mainly used by `HomepageState.init`.
- `clearAll()` on logout; `clearCheckpoints()` supports forced refresh.

### CheckpointMixin (`lib/core/local_storage/checkpoint_mixin.dart`)

- `saveMaxTimestampCheckpoint` / `...FromItems` - persists the max `created_at` across fetched items, or `EMPTY`. Used by feature states to drive `hasChanges`-based incremental refresh (cache -> network only when data changed).

## Navigation & Screen Hierarchy

- **Root navigator key**: `ErrorHandler.navigatorKey` (global static). `CaptchaService` and the reauth dialog rely on it.
- **Named routes** exist (`/login`, `/register`, `/homepage`, `/partner`, `/localization`, `/change-password`) but startup and auth flows use inline `MaterialPageRoute` pushes. Only `/localization` and `/change-password` are commonly reached via name; the error reauth dialog uses `pushNamedAndRemoveUntil('/login', ...)`.
- **`/homepage` route** and the two startup `pushReplacement`s all construct `MainShell(key: MainShell.shellKey)` - one shared static `GlobalKey<MainShellState>` across three code sites (see Findings).

### MainShell - 7-tab IndexedStack

`lib/features/home/screens/main_shell.dart`:

- `static GlobalKey<MainShellState> shellKey` + `switchToTab(index)` - cross-tab deep navigation from feature screens (homepage "Mood"/"List"/"Favorites" buttons call `MainShell.shellKey.currentState?.switchToTab(...)` at homepage_screen.dart lines 193/369/471/530).
- `IndexedStack` inside a `Padding(bottom: 110)`; the floating bottom nav (`HomeBottomNav`) overlays.
- **Lazy building**: `_builtPages` starts `{0}` and only pages already visited are materialized (`List.generate(7, ...)` yields `SizedBox.shrink()` for unvisited). Tab order: Home(0) always, Games(1), Mood(2), List(3), Drive(4), Favorites(5), Profile(6).
- `TabIndexNotifier` shared with tab screens.

### TabScreen / TabScreenMixin (`lib/shared/widgets/tab_screen.dart`)

- `TabScreen` base requires `tabIndex` + `tabNotifier`.
- `TabScreenMixin` listens to the notifier and loads data on **first activation** and on **every switch back** to the tab (`_dataLoadedOnce` reset). `loadData({force})` is the override point (pull-to-refresh uses `force: true`).
- Applied to `GameScreen`, `MoodScreen`, `BucketListScreen`, `DriveScreen`, `FavoritesScreen`. `HomepageScreen` (index 0) and `ProfileScreen` (const, no notifier) manage their own post-frame loads instead.

**Key gap**: lazy tab building only defers *data loading and widget construction*, not state/realtime subscriptions - all feature states and the `RealtimeSyncService` are live from app start (see Findings).

## Lazy Tab Architecture

- `MainShell` lazily builds tab widgets via `_builtPages`; `TabIndexNotifier`/`TabScreenMixin` trigger per-tab data loads on activation.
- States themselves are eager (created in `MultiProvider`), so the "laziness" is UI-only.
- Realtime events refresh feature states regardless of which tab is active (`RealtimeSyncService._refreshAll()` fans out to all seven states).
- `IndexedStack` keeps all visited tabs alive (state preserved when switching); only the active tab is visible, so tab state is never disposed during a session.

## Realtime Initialization

### Wiring (`lib/core/realtime/realtime_sync_scope.dart`)

- `RealtimeSyncScope` sits between `MultiProvider` and `MaterialApp`, so it can read all states.
- `didChangeDependencies` -> creates `RealtimeSyncService(all states).start()` once.
- A `Consumer2<AuthState, PartnerState>` schedules exactly **one post-frame `configure()`** per dependency pass via `_configureScheduled`; resolves `partnershipId` preferring `authState.partnershipId` and falling back to `partnerState.partnershipInfo?.partnershipId`.
- The service is exposed as `Provider<RealtimeSyncService>.value` (consumed by e.g. `ProfileScreen._showWipeConfirmation`).
- Service lifecycle is tied to this widget's `dispose()`.

### Service (`lib/core/realtime/realtime_sync_service.dart`)

- `start()`: registers as `WidgetsBindingObserver`, subscribes to `auth.onAuthStateChange`. On `tokenRefreshed` -> `realtime.setAuth(token)` without reconnect. Any other auth event while foreground+user -> `_scheduleReconnect()`.
- `configure(userId, partnerId, partnershipId)`: resets retry counters; if `userId` or `partnershipId` is null -> unsubscribe and defer; else (on change) `_scheduleReconnect`.
- Subscribes to **8 tables** on one channel `justus-sync-<userId>-<generation>`: `moods`, `partnerships`, `missyou`, `bucket_items`, `game_questions`, `game_answers`, `drive_items`, `drive_item_reactions`.
- Event routing: per-table relevance filter (`_isRelevantMood/Partnership/MissYou/Game/Drive`) + dedup (`_markSeen`, LRU of 80 `table:event:id:commitTimestamp` keys) + debounced timers (120-150 ms) into feature states (`refreshFromRealtime(...)`, `applyRealtimeEvent(...)`, `handleQuestionInsert/Update/Delete`, `handleAnswerInsert/Update/Delete`, `addMissYou`).
  - `game_questions` **insert/delete are processed immediately** (not debounced) to avoid drops.
  - Miss-you **insert** optimistically increments `HomepageState.addMissYou()`; **delete** triggers a full refresh.
  - Partnership events trigger BOTH `PartnerState.refreshFromRealtime()` and `AuthState.refreshPartnershipFromRealtime()` plus `BaseRepository.clearPartnershipCache()`.
- **Reconnection**: exponential backoff 1s -> 60s (`1 << clamp(0..7)`, base 3s for close code 1002, jitter up to +/-25%), max 20 attempts (`_reconnectAttempt`), de-duplicated by the `_subscribing` guard and a generation counter (stale channel callbacks are ignored).
- **Polling fallback**: after 3 consecutive failures, `_activatePollingFallback()` starts `Timer.periodic(15s)` -> `_refreshAll()` (8 table queries), deactivated on a successful subscribe or on `configure`.
- **Lifecycle**: resumed -> 300ms debounce then `_scheduleReconnect(refreshAfterSubscribe: true)`; paused/hidden/detached -> `_unsubscribe()`; inactive -> no-op. `_foreground` guards all subscribe paths.
- `suppress()` sets `_suppressProcessing = true` (used by the Profile data-wipe); `resume()` exists but **is never called** (suppression is actually reset by the next `_subscribe()`); `refreshChannel()` forces an unsubscribe/resubscribe with refresh (used after wipe).
- Dead field: `_missYouRefreshTimer` is declared but never assigned.

## Notifications Initialization

### Main-process init (`lib/main.dart` -> `NotificationService.init()`)

`lib/core/notifications/notification_service.dart` (singleton):

1. `_requestRemoteNotificationPermission()` (mobile/web only, errors swallowed).
2. `initLocalNotifications()`:
   - Platform settings (Android `ic_notification`, iOS/macOS Darwin, Linux, Windows with app id `com.justus.app`).
   - Plugin initialize with a global `onDidReceiveNotificationResponse` -> push tap payload into the broadcast `onNotificationTap` stream.
   - Android `justus_channel` creation + permission request (skipped in background).
3. Mobile/web only: `setForegroundNotificationPresentationOptions(...)`; launch notification payload -> `onNotificationTap` after a 500ms delay; `FirebaseMessaging.onMessage.listen(showRemoteMessage)` (foreground handler, registered once).

### Background handler (`lib/main.dart`)

`_firebaseMessagingBackgroundHandler` (`@pragma('vm:entry-point')`):

- **Early-returns if `message.notification == null`** -> data-only messages are dropped in the background/terminated case.
- Initializes `WidgetsFlutterBinding`, Firebase (mobile/web), locale from system, then `initLocalNotifications(isBackground: true)` + `showRemoteMessage(isBackground: true)`.

### Localization of notification text

- `showRemoteMessage` reads the saved locale (`SharedPreferences` via `LanguageHelper.storageKey`) else the system locale, then localizes by `data['notificationKey']` among 8 keys (`requestAccepted`, `missyou`, `moodUpdated`, `answerSubmitted`, `newQuestion`, `driveItemAdded`, `reactionAdded`, `bucketItemAdded`); fallback -> raw `title`/`body`, or (if both absent) **silently returns without showing**.
- Unknown `notificationKey` fallback -> `(title: 'JustUS', body: '')` - an empty-body notification.
- Stable notification IDs: `data['notificationId']` or `messageId` hashed (djb2); otherwise an incrementing in-process counter.

### Push send path (outbound)

Feature actions call `BaseRepository.notifyPartnerOnce(notificationKey, params)` -> transient `ApiService.notifyPartner(...)` -> backend `POST /api/v1/notify/partner` -> FCM via Firebase Admin (backend responsibility). The receiver localizes the server-agnostic `notificationKey` + `params` on the device.

## Session Initialization

`AuthState.init()` (`lib/features/auth/auth_state.dart`):

1. Sets `ApiService.onSessionExpired` -> forced `logout()`. (Global mutable callback, overwritten on every call.)
2. Cancels prior `_authSubscription`/`_tokenRefreshSubscription` (makes init re-runnable).
3. **Parallel** secure-storage reads via `Future.wait`: access token, refresh token, username, user id, partner id, partner display name, partnership id.
4. Supabase session check:
   - No session + local access token -> `logout()` (clears cache).
   - Session present + username missing -> `fetchProfileByAuthId` + `setLoginData`.
5. `_syncBackendSession()`: POST `/auth/session-sync` with device fingerprint + device label; stores binding secret. Failures logged only.
6. If logged in + FCM: `updateDeviceToken(token, locale)` (backed by `AuthRepository.updateDeviceToken`, which is signed). Failures logged only.
7. Subscribes to `auth.onAuthStateChange` (`tokenRefreshed` -> persist tokens) and `DeviceTokenService.onTokenRefresh` (re-register device token).
8. Registers `this` as `WidgetsBindingObserver` -> resumed -> debounced locale sync; `didChangeLocales` -> locale sync.
9. Calls `notifyListeners()`.

## Error Handling Initialization

`ErrorHandler` (`lib/core/error_handling/error_handler.dart`) is purely static - no explicit init needed.

- `navigatorKey` is a `static final GlobalKey<NavigatorState>` used by: (a) `MaterialApp.navigatorKey` in `main.dart`, (b) `CaptchaService.getCaptchaToken()` which needs a `BuildContext` for the Turnstile dialog, (c) `ErrorHandler._showReauthDialog` / `ErrorHandler.handleGlobal` which navigate without a widget context.
- `FlutterError.onError` is wired in `main()` step 2; `runZonedGuarded` catches uncaught zone errors in step 1.
- `ErrorHandler._showSnackBar` uses an `OverlayEntry` via the root navigator overlay (NOT `ScaffoldMessenger`). It is aware of scheduler phases and defers insertion to the next frame when called during build. A `Future.delayed(4s)` removes it in release; in debug it persists until dismissed.
- `ErrorDialog` (reusable widget in `shared/design_system/error_dialog.dart`) shows error code only in debug mode (`kDebugMode`). The reauth dialog navigates to `/login` via `pushNamedAndRemoveUntil`, clearing the navigation stack.
- `AppError` (`lib/core/error_handling/app_error.dart`) supports factories: `.network()`, `.timeout()`, `.fromException()`, `.fromJson()` (from backend envelope). `ErrorCodes` maps codes to localized user messages and classifies severity/reauth requirements.

### Logging

`AnsiLogger` (`lib/core/utils/ansi_logger.dart`) provides colored ANSI-tagged debug output with named channels: `.auth()`, `.api()`, `.realtime()`, `.notification()`, `.supabase()`, `.error()`. All logging is console-only in the Flutter app (no remote logging in Flutter; the backend writes to Supabase `logs_*` tables).

## Version Checking

- `UpdateService` (`lib/core/version/update_service.dart`) is instantiated in `HomepageScreen.initState()` (a local instance variable).
- Guarded by `_updateChecked` (runs once per `HomepageScreen` lifecycle) and `_isDialogShowing` (prevents duplicate dialogs). Skipped on web (`kIsWeb`).
- Flow: reads local `PackageInfo.buildNumber` -> calls `VersionRepository.checkAppVersion()` (backend `GET /api/v1/app-version`, skip auth, 10s timeout) -> compares local build vs server build. If local < server, shows `VPDialog` with changelog; mandatory if `forceUpdate` or local < `minBuild`.
- The update dialog offers "later" (non-mandatory only, Android/Windows) or "now" (launches APK URL via `url_launcher`).

## Lifecycle Handling

Three components register as `WidgetsBindingObserver`:

1. **AuthState** (`lib/features/auth/auth_state.dart`):
   - `didChangeAppLifecycleState(resumed)` -> debounce 500ms -> `_syncDeviceLocale()` (updates the `locale` field in the backend device token if changed; FCM-supported platforms only).
   - `didChangeLocales(locales)` -> `_syncDeviceLocale(locales.first)` (immediate, no debounce).
   - Cleanup: `dispose()` removes observer and cancels locale-sync debounce timer.

2. **RealtimeSyncService** (`lib/core/realtime/realtime_sync_service.dart`):
   - `didChangeAppLifecycleState(resumed)` -> 300ms debounce -> `_scheduleReconnect(refreshAfterSubscribe: true)`.
   - `didChangeAppLifecycleState(paused/hidden/detached)` -> `_unsubscribe()` (cancels reconnect timers, removes channel).
   - `didChangeAppLifecycleState(inactive)` -> no-op.
   - Cleanup: `dispose()` removes observer, cancels all timers, cancels auth subscription, unsubscribes.

3. **Background message handler** (top-level `_firebaseMessagingBackgroundHandler` in `main.dart`):
   - Only runs in a separate isolate (when the OS delivers a background/terminated FCM message). Calls `WidgetsFlutterBinding.ensureInitialized()` independently.

## Architectural Findings & Violations

### F1: Global mutable state scattered across static fields

**Evidence**: `ApiService.onSessionExpired` (static, set by `AuthState.init()`); `ApiService._cachedDeviceFingerprint` / `_cachedRequestBindingSecret` (static, mutated from `StorageService.saveRequestBindingSecret` and `ApiService._buildHeaders`); `ErrorHandler.navigatorKey` (static GlobalKey); `MainShell.shellKey` (static GlobalKey).

**What**: Multiple singletons hold mutable state via static fields rather than being injected. The `onSessionExpired` callback is a static `Function?` that is overwritten every time `AuthState.init()` runs.

**Impact**: Makes unit testing harder (state bleeds between tests unless manually cleared). The coupling between `StorageService` and `ApiService` via static mutation (`setCachedRequestBindingSecret`) creates a hidden bidirectional dependency.

**Confidence**: HIGH (verified at auth_state.dart:179, api_service.dart:19-23, api_service.dart:46-55).

### F2: Homepage avatars bypass protected URL resolution

**Evidence**: `homepage_screen.dart:674` - `_AvatarColumn` renders `Image.network(imageUrl!)` directly using `profilePicUrl` from the Supabase `user_profiles` table. Contrast with `VPAvatar` (vp_widgets.dart) and `VPMiniAvatar` (vp_mini_avatar.dart:17-29), both of which call `ApiService.resolveProtectedMediaUrl(imageUrl)` first.

**What**: Profile pictures in Supabase `user_profiles.profile_pic_url` are stored as R2 object keys (e.g. `drive/profile/{userId}/...`), not full HTTP URLs. `resolveProtectedMediaUrl()` rewrites these into `GET /api/v1/media/file?filename=...`. Without this rewrite, `Image.network` attempts to fetch a relative path as an HTTP URL and fails.

**Impact**: The homepage partner avatar always fails to load and shows the errorBuilder placeholder (default person icon). The profile screen avatars work correctly because they use `VPAvatar` which resolves the URL.

**Confidence**: MEDIUM - depends on the exact semantics of `profilePicUrl` at the time `HomepageScreen` renders. The upload flow (`profile_state.dart:113`) stores the r2Path from `MediaService.uploadProfilePicture`, which is the object key. If `v_active_partnership` or `fetchProfileByAuthId` returns a full URL instead, this would not be a bug. However, the codebase evidence (object key storage, backend `r2.service.js` object-key construction) strongly suggests it is an object key.

### F3: `RealtimeSyncService.resume()` is never called

**Evidence**: `resume()` is declared at realtime_sync_service.dart. `suppress()` is called only at profile_screen.dart:95 (after data wipe). No call to `resume()` exists anywhere in the codebase (grep confirmed).

**What**: After `suppress()` is called during a data wipe, event processing is re-enabled by the subsequent `_subscribe()` call inside `refreshChannel()`, which resets `_suppressProcessing = false`. The public `resume()` method is dead code.

**Impact**: No functional impact currently (the wipe flow works via `refreshChannel()`), but the dead API is misleading for future developers who may call `resume()` expecting it to restore event processing.

**Confidence**: HIGH.

### F4: `_missYouRefreshTimer` is declared but never used

**Evidence**: `Timer? _missYouRefreshTimer` declared in `realtime_sync_service.dart` but never assigned or read anywhere in the class.

**What**: Dead field, presumably intended for debounced miss-you refresh but replaced by the inline logic in `_handleMissYouPayload` (direct optimistic increment on insert, refresh on delete).

**Impact**: No functional impact. Minor code hygiene.

**Confidence**: HIGH.

### F5: Shared `GlobalKey<MainShellState>` used across three independent code paths

**Evidence**: `MainShell.shellKey` is a `static final GlobalKey` at main_shell.dart:5. It is used in: (a) the `/homepage` named route (main.dart), (b) `SplashScreen._checkAuth` (splash_screen.dart:39), (c) `LoginScreen` (login_screen.dart:112). In all three cases: `MainShell(key: MainShell.shellKey, ...)`.

**What**: `GlobalKey` requires that only one instance with that key is mounted in the widget tree at any time. If the `/homepage` named route were ever pushed while another `MainShell` was already mounted (e.g. via named-route-based navigation), a "Multiple widgets used the same GlobalKey" error would occur. Currently, `SplashScreen` and `LoginScreen` use `pushReplacement` (removing the previous route), so the risk is low.

**Impact**: Low risk under current navigation patterns. However, mixing named routes and direct MaterialPageRoute pushes to the same widget with a GlobalKey is fragile.

**Confidence**: HIGH (the global key is verified at main_shell.dart:5, splash_screen.dart:39, login_screen.dart:112, main.dart routes map).

### F6: Eager provider creation defeats lazy tab architecture

**Evidence**: All 11 providers are created in `MultiProvider` at `main.dart:96-111`. `MainShell._builtPages` at main_shell.dart:17 lazily builds tab widgets only.

**What**: Feature states (and their repositories -> `ApiService` instances -> `http.Client` instances) are created at app startup regardless of whether the user ever visits those tabs. The "lazy" architecture only defers widget construction and `loadData()` calls; the state objects and all their dependencies (networking, storage) exist from the start.

**Impact**: Unnecessary memory consumption at startup. Each `ApiService` creates its own `LoggingHttpClient(http.Client())`, so there are ~10 `http.Client` instances alive at all times (one per default-constructed `ApiService` in feature repos). For a couples app this is acceptable but architecturally wasteful.

**Confidence**: HIGH.

### F7: Hidden initialization requirement - binding secret

**Evidence**: `ApiService._buildHeaders` at api_service.dart:64-90: if `method` + `path` are provided AND `bindingSecret` is null/empty AND `requireSignature: true`, the method throws `HttpException('Missing request binding secret')`. The binding secret is only obtained from `_syncBackendSession()` (auth_state.dart:337-359), which is called inside `AuthState.init()`. If `_syncBackendSession()` fails (network error, backend down), the binding secret is never saved, and all signed endpoints silently fail with `NetworkError`.

**What**: Three endpoint categories require the binding secret: device-token registration, media presign/complete, and AI question generation. A backend outage during app initialization will cause all these features to break until the next successful session sync. The failure manifests as a generic `NetworkError` with no specific guidance.

**Impact**: Signed features silently broken after initialization failure. No automatic retry mechanism exists to re-obtain the binding secret on subsequent app uses (init only runs once per cold start).

**Confidence**: HIGH.

### F8: Dual token-refresh can race

**Evidence**: Supabase client's built-in token refresh fires `onAuthStateChange(tokenRefreshed)` (auth_state.dart:322-331), which saves to `StorageService`. Separately, `ApiService._tryRefreshToken()` (api_service.dart:307-338) calls the backend `/auth/refresh` proxy and also saves to `StorageService` (same keys). Both can fire concurrently.

**What**: If Supabase refreshes the token and simultaneously `ApiService` gets a 401 and triggers `_tryRefreshToken`, two refresh requests may fire in parallel, and one may overwrite the other's tokens (the refresh token from the Supabase response may differ from the backend-proxied refresh token, or vice versa).

**Impact**: Possible token inconsistency. In practice, the `_isRefreshing` flag in `ApiService` prevents concurrent refresh attempts, but does not prevent the Supabase client from refreshing independently.

**Confidence**: MEDIUM.

### F9: `ProfileState.loadProfile()` silently skips when already loading

**Evidence**: `profile_state.dart:37` - `if (isLoading) return;` is the first line of `loadProfile()`, before the cache-read path.

**What**: If `loadProfile()` is called while a previous `loadProfile()` call is in progress (e.g. `HomepageScreen._loadData()` and `ProfileScreen.initState()` both call it on startup), the second call silently returns without reading from cache or network. This means the homepage or profile screen may see stale/empty state until the first load completes.

**Impact**: The homepage profile section may show no avatar/name during the first few hundred milliseconds after startup if both screens load in rapid succession.

**Confidence**: HIGH.

### F10: Token refresh race between `AuthState._accessToken` and `Supabase` session

**Evidence**: `AuthState` maintains its own `_accessToken` (auth_state.dart:41) but `ApiService._getHeaders()` reads the token from `Supabase.instance.client.auth.currentSession?.accessToken` (api_service.dart:58). `AuthState.isLoggedIn` checks `_accessToken != null` (auth_state.dart:70).

**What**: After logout, `AuthState.logout()` clears `_accessToken` and `StorageService`, then calls `_authRepo.signOut()` (which clears the Supabase session). But `ApiService._safeCall` reads from `Supabase.instance.client.auth.currentSession` directly - if the Supabase session is cleared asynchronously, a brief window exists where `ApiService` sees a stale session while `AuthState` thinks it is logged out.

**Impact**: Edge case: after logout, a concurrent in-flight API request may still succeed with the old Supabase token before it is revoked.

**Confidence**: LOW (Supabase's `signOut()` is synchronous and clears the in-memory session immediately).

### F11: `PartnershipRepository.rejectPartnerRequest` deletes directly via Supabase

**Evidence**: `partnership_repository.dart:134-142` - `rejectPartnerRequest` does `sbClient.from('partnerships').delete().eq('id', partnershipId).eq('status', 'pending')` directly, bypassing the backend.

**What**: This means the delete goes through RLS (which should be fine - only the partnership members can delete their own pending row), but unlike `acceptPartnerRequest` (which calls an RPC), the rejection does not fire a notification to the other party. The backend `invite` endpoint and `request_partnership` RPC also do not notify on reject.

**Impact**: No notification is sent to the sender when their partnership request is rejected. This may or may not be intended behavior; it is a functional asymmetry.

**Confidence**: MEDIUM.

### F12: Two separate snackbar display mechanisms

**Evidence**: `ErrorHandler._showSnackBar` (error_handler.dart:146-200) uses a root `OverlayEntry`. `UIUtils.showSnackBar` (snackbar_utils.dart:11-40) uses `ScaffoldMessenger`.

**What**: Two independent snackbar mechanisms coexist. `ErrorHandler` creates a global overlay snackbar that overlays everything (including the nav bar). `UIUtils` uses the standard `ScaffoldMessenger`. Both can display simultaneously, leading to visual stacking.

**Impact**: Minor UX inconsistency - error snackbars from `ErrorHandler` appear above the nav bar (global overlay) while success snackbars from `UIUtils` appear within the scaffold.

**Confidence**: HIGH.

### F13: `HomepageScreen` bypasses `TabScreenMixin` and `TabIndexNotifier`

**Evidence**: `HomepageScreen` (index 0) is built directly by `MainShell._pageWidget(0)` and always included in `_builtPages`. It does not take `tabIndex`/`tabNotifier` parameters and does not use `TabScreenMixin`.

**What**: When the user switches away from the homepage and back, `HomepageScreen` does NOT reload data (it only loaded once in `initState` via `addPostFrameCallback`). Other tabs (Mood, Bucket, etc.) reload on every switch-back via `TabScreenMixin._onTabChanged`.

**Impact**: The homepage always shows stale data after the user navigates to another tab and back, unless they pull-to-refresh manually. For example, a miss-you count sent by the partner while the user was on the Mood tab will be missed until they navigate back to Home.

**Confidence**: HIGH.

## Notes

- **No dependency injection container.** All repos and services are constructed via `new` with optional constructor injection for testability. Production code always uses default constructors. This means, for example, every `PartnershipRepository()` instance (there are at least 3: one in `AuthState`, one in `PartnerState`, one in `ProfileState`) creates its own `ApiService` with a fresh `http.Client`.
- **`all_imports.dart` barrel** is auto-generated via `tool/generate_imports.js` (pre-commit hook). It exports 100+ files. While this simplifies imports, it means every file transitively depends on every other file, making the dependency graph circular at the package level.
- **No offline queue.** Network failures during user actions (e.g. send miss-you, add bucket item) are not retried. The user must attempt again manually.
- **`BaseState.loadWithChangeDetection`** fires `fetchFromNetwork` as `unawaited` with `.catchError`, so network failures during background refresh are silently logged via `ErrorHandler.handle` (which may show a snackbar). This means users occasionally see snackbar errors from invisible background refresh failures.
- **`AuthState._emailRedirectTo`** returns a server callback URL for web/desktop and `justus://auth/callback` for mobile deep links. The `/auth/callback` endpoint renders a static HTML page (`templates/callbackPage.js`), not a deep link handler.
- **Platform support**: Android, iOS, macOS, Windows, Web. No Linux. FCM is Android/iOS/Web only; macOS and Windows use device fingerprint as the token. Desktop notifications are handled by `flutter_local_notifications` (Windows/Linux support in that package).
