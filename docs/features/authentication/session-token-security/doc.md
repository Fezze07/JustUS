# Session & Token Security - JustUS

## Overview

This document provides a comprehensive reverse-engineered analysis of the **Session & Token Security** system in the JustUS application. It documents the complete lifecycle of authentication tokens, session persistence, automatic token refresh, HTTP 401 error handling, JWT verification, session binding protections (`auth_sessions`), session synchronization (`/auth/session-sync`), and HMAC request signing with binding secrets.

The session security model in JustUS is a multi-layered defense system:
- **Identity Provider (Supabase Auth)**: Issues Access Tokens (JWT) and Refresh Tokens.
- **Client Storage & Networking (Flutter)**: Manages secure token storage (`FlutterSecureStorage`), headers injection, request signing, and single-retry 401 recovery (`ApiService`).
- **Backend Middleware (Node.js / Express)**: Enforces Supabase token verification (`authSupabase.auth.getUser`), token lifetime policy checks, device fingerprint and user-agent binding validation, soft IP range change logging, and HMAC signature verification (`requireSignedRequest`).

## Token Lifecycle

### Token Properties & Origin

- **Access Token**: JSON Web Token (JWT) generated by Supabase Auth server upon login, registration, or session refresh.
- **Refresh Token**: Opaque string generated by Supabase Auth for acquiring fresh access tokens.
- **Storage Location**: Client-side storage via `FlutterSecureStorage` (managed by `StorageService`).

### Token Lifetime & Policy Enforcement

- File: [tokenUtils.js](file:///f:/JustUS/Backend/utils/auth/tokenUtils.js#L27-L36) & [env.js](file:///f:/JustUS/Backend/config/env.js#L30)
- Configured Constant: `MAX_ACCESS_TOKEN_LIFETIME_SEC` in `Backend/config/env.js`.
  - Default Value: `900` seconds (15 minutes).
- **Backend Policy Verification**:
  ```javascript
  function validateTokenLifetime(claims, maxLifetimeSec) {
    const issuedAt = Number(claims.iat ?? 0);
    const expiresAt = Number(claims.exp ?? 0);
    
    if (issuedAt && expiresAt) {
      const tokenLifetime = expiresAt - issuedAt;
      if (tokenLifetime > maxLifetimeSec) {
        throw new Error("Token lifetime exceeds policy");
      }
    }
  }
  ```
- If a JWT is issued with a lifetime greater than `maxAccessTokenLifetimeSec` (e.g., Supabase default 3600 seconds / 1 hour), `authMiddleware` throws an error, resulting in `AUTH_FAIL_001`.

## Refresh Flow

### Protocol & Mechanism

- File: [api_service.dart:279-316](file:///f:/JustUS/Flutter/lib/core/network/api_service.dart#L279-L316) & [auth.controller.js:184-198](file:///f:/JustUS/Backend/features/auth/auth.controller.js#L184-L198)
- Token refresh is **backend-mediated**. The Flutter client does not call Supabase Auth directly for refreshes; it sends a request to the Node.js API backend.

```
Flutter Client                           Node Backend                     Supabase Auth
      │                                       │                                 │
      │── POST /api/v1/auth/refresh ─────────>│                                 │
      │   { refreshToken }                    │── refreshSession(refreshToken)─>│
      │                                       │   (authSupabase.auth)           │
      │                                       │<── New Tokens (access/refresh)──│
      │<── { accessToken, refreshToken } ─────│                                 │
```

### Concurrency Protection & Race Conditions

- `ApiService` uses an in-memory boolean flag `_isRefreshing = false` during refresh operations.
- If an API call receives HTTP 401 while `_isRefreshing` is `true`, `_safeCall` bypasses triggering a second refresh attempt and immediately returns `GenericError(code: 401)`.
- Multiple simultaneous 401 responses do **not** enqueue or wait for the active refresh to finish; secondary requests fail immediately.

## 401 Handling & Request Retry

### Retry Logic (`_safeCall`)

- File: [api_service.dart:152-222](file:///f:/JustUS/Flutter/lib/core/network/api_service.dart#L152-L222)
- When an HTTP response status code is `401`, `_safeCall` evaluates:
  ```dart
  if (response.statusCode == 401 && !isRetry && !_isRefreshing) {
    final refreshResult = await _tryRefreshToken();
    if (refreshResult) {
      return await _safeCall(call, fromJson, isRetry: true, timeout: timeout, label: label);
    }
    await onSessionExpired?.call();
    return const GenericError(code: 401, message: 'Session expired. Please login again.');
  }
  ```

### Header Rebuilding & Signature Regeneration

When retrying an HTTP `POST` or `GET` request:
1. `call()` re-invokes `_buildHeaders()`.
2. Generates a fresh timestamp (`X-Request-Timestamp = DateTime.now()`) and fresh UUID nonce (`X-Request-Nonce = _uuid.v4()`).
3. Re-computes the HMAC-SHA256 signature (`X-Request-Signature`) using the updated timestamp, nonce, canonical path, and payload hash.

### Retries Allowed

- Exactly **1 retry** is permitted (`isRetry: true`). If the retried request fails with 401, no further retries occur.

## JWT Verification

Backend token verification is executed by `authenticateToken` middleware on every protected route.

- File: [authMiddleware.js](file:///f:/JustUS/Backend/middleware/authMiddleware.js)

### Verification Steps

1. **Token Extraction**: Extracts Bearer token from `Authorization` header.
2. **Supabase getUser Verification**:
   - Calls `authSupabase.auth.getUser(token)`.
   - Makes a remote RPC request to Supabase Auth server to confirm the token is valid, active, and unrevoked.
3. **Claims Decoding & Lifetime Validation**:
   - Decodes JWT payload (`decodeTokenClaims`).
   - Asserts `claims.role === "authenticated"`.
   - Checks `validateTokenLifetime(claims, env.maxAccessTokenLifetimeSec)`.
4. **Database Profile Lookup**:
   - Queries `public.users` via `adminSupabase` matching `auth_id = user.id`.
   - Loads internal integer `profile.id`, display name, user roles, and capabilities (`resolveCapabilities`).

## Session Binding

JustUS enforces strict session binding to ensure stolen JWT tokens cannot be used from unauthorized devices or browsers.

- Files: [requestFingerprintService.js](file:///f:/JustUS/Backend/services/requestFingerprintService.js) & [session.utils.js](file:///f:/JustUS/Backend/features/auth/session.utils.js)

### Bound Parameters Specification

| Parameter | Header / Source | Generation / Format | Storage (`auth_sessions`) | Validation Action |
|---|---|---|---|---|
| Device Fingerprint | `X-Device-Fingerprint` | Client UUID stored in secure storage | `device_fingerprint_hash` (SHA-256) | Strict match (`AUTH_FAIL_006`) |
| Client User-Agent | `X-Client-User-Agent` | `justus/flutter/{platform}` | `user_agent_hash` (SHA-256) | Strict match (`AUTH_FAIL_006`) |
| Soft IP Range | Request IP (`req.ip`) | IPv4 `/24` or IPv6 first 4 segments | `ip_range` | Soft check (Logs `ip_range_changed`) |
| Behavior Pattern | HTTP Headers | Hash of fingerprint, UA, IP range, language & headers | `request_profile_hash` | Monitored during session sync |

### Validation Implementation

- File: [session.utils.js:9-39](file:///f:/JustUS/Backend/features/auth/session.utils.js#L9-L39)
```javascript
function validateSessionBinding(sessionBinding, clientContext) {
  checkRevocation(sessionBinding);
  checkDeviceFingerprint(sessionBinding, clientContext);
  checkUserAgent(sessionBinding, clientContext);
}
```
- If `device_fingerprint_hash` or `user_agent_hash` differs from the active request context, backend throws `AppError(AUTH_FAIL_006)` ("Client binding mismatch. Please login again.").
- Soft IP range changes do **not** block the user. If the client moves between networks (e.g. WiFi to LTE), `isIpRangeChanged` evaluates to `true`, and backend logs a security audit event (`ip_range_changed`).

## Session Sync (`/auth/session-sync`)

### Route & Controller Specification

- Endpoint: `POST /api/v1/auth/session-sync`
- File: [auth.routes.js:87-96](file:///f:/JustUS/Backend/features/auth/auth.routes.js#L87-L96) & [auth.controller.js:108-131](file:///f:/JustUS/Backend/features/auth/auth.controller.js#L108-L131)
- Middleware Stack: `authenticated()`, `limited(authRateLimit)`, `freshNonce("auth-session-sync")`, `validated({ body: sessionSyncSchema })`.

### Functionality

1. Calls `trackSession()` in [authRisk.service.js](file:///f:/JustUS/Backend/features/auth/authRisk.service.js#L95-L125).
2. Upserts record into `auth_sessions` PostgreSQL table using key `session_id` (or fallback `${userId}:${deviceFingerprintHash}`).
3. Generates a new 32-byte hex `bindingSecret` (or reuses existing binding secret for the session).
4. Detects session anomalies (`ip_changed`, `country_changed`, `behavior_pattern_changed`) and logs security events.
5. Invokes `clearFailedLogins()` to reset failed login counters for the IP / device / email key.
6. Returns `{ success: true, anomalies, bindingSecret }`.

## Binding Secret & HMAC Request Signing

### HMAC Relationship

- **Purpose**: High-risk routes (`/device-token`, `/media/upload-url`, `/media/complete`, `/ai/question`) require request signing via `signed()` / `requireSignedRequest()` middleware to prevent request tampering and replay attacks.
- **Secret Generation**: Created via `crypto.randomBytes(32).toString("hex")` in `generateBindingSecret()`.
- **Secret Lifecycle**:
  - Generated on backend during `/auth/session-sync`.
  - Transmitted to Flutter client in the sync response payload.
  - Saved in Flutter secure storage (`StorageService.saveRequestBindingSecret`) and cached in `ApiService`.
  - Reused for all HMAC signatures during the active session.
  - Invalidated when `auth_sessions` record is deleted or revoked (`revoked_at != null`).

### Canonical Request Signature Format

- File: [requestSigningService.js:8-16](file:///f:/JustUS/Backend/services/requestSigningService.js#L8-L16)
```
CanonicalString = METHOD . PATH . TIMESTAMP . NONCE . BODY_HASH
Signature = HMAC-SHA256(bindingSecret, CanonicalString)
```

## Error Handling

### Error Code Reference Matrix

| Error Code | HTTP Status | Trigger Condition | Consequence |
|---|---|---|---|
| `AUTH_FAIL_001` | 401 | Invalid / expired Supabase token, or token lifetime exceeds policy | Triggers client refresh attempt |
| `AUTH_FAIL_002` | 401 | Missing Bearer token in Authorization header | Aborts request |
| `AUTH_FAIL_003` | 401 | Session explicitly revoked (`revoked_at` is set in `auth_sessions`) | Forces logout |
| `AUTH_FAIL_004` | 401 | Token role claims !== `'authenticated'` | Aborts request |
| `AUTH_FAIL_005` | 401 | User profile not found in `public.users` table | Aborts request |
| `AUTH_FAIL_006` | 401 | Device Fingerprint or User-Agent binding mismatch | Forces re-login |
| `SEC_AUTH_002` | 401 | Missing, expired, or invalid HMAC request signature | Rejects signed request |
| `SEC_BLOCK_001` | 400/403 | Replay attack detected (request nonce already consumed) | Rejects request |

## Security Properties

1. **Anti-Token Hijacking**: Stolen JWTs cannot be used on an attacker's device without matching both `X-Device-Fingerprint` and `X-Client-User-Agent` hashes stored in `auth_sessions`.
2. **Replay & Tamper Protection**: Signed API routes enforce a 5-minute timestamp skew window (`REQUEST_SIGNING_MAX_SKEW_MS`) and consume single-use nonces stored in Redis/Memory (`consumeNonce`).

## Potential Bugs and Inconsistencies

### 1. CRITICAL BUG: Token Refresh Desynchronization (Broken 401 Retry)
- **Finding**: In `ApiService._tryRefreshToken()` ([api_service.dart:299](file:///f:/JustUS/Flutter/lib/core/network/api_service.dart#L299)), when `POST /api/v1/auth/refresh` returns a new access token, `ApiService` saves it to secure storage via `StorageService.saveAccessToken(newAccessToken)`.
- **Defect**: `_tryRefreshToken()` **never updates the internal Supabase SDK session** (`Supabase.instance.client.auth`).
- **Impact**: When `_safeCall` retries the original API request, `_buildHeaders()` fetches `Supabase.instance.client.auth.currentSession?.accessToken` ([api_service.dart:88](file:///f:/JustUS/Flutter/lib/core/network/api_service.dart#L88)), which still contains the **old expired token**. The retried request fails with 401 a second time. Because `isRetry == true`, `_safeCall` invokes `onSessionExpired?.call()`, forcing an immediate logout despite a successful token refresh.

### 2. CONFIGURATION MISMATCH: Hardcoded Token Lifetime Rejection
- **Finding**: `Backend/config/env.js:30` sets `maxAccessTokenLifetimeSec` to default `900` seconds (15 minutes).
- **Defect**: In `tokenUtils.js:33`, `validateTokenLifetime()` throws `"Token lifetime exceeds policy"` if `exp - iat > maxAccessTokenLifetimeSec`.
- **Impact**: If Supabase Auth is configured to issue JWTs with a default 1-hour (3600 seconds) lifetime, the Node backend will immediately reject valid Supabase JWTs with `AUTH_FAIL_001`.

### 3. CONCURRENCY BUG: Unhandled Concurrent 401 Requests
- **Finding**: `ApiService._isRefreshing` guards against multiple refresh calls.
- **Defect**: If multiple asynchronous API requests fail with 401 simultaneously, the first request sets `_isRefreshing = true` and begins refreshing. The secondary requests inspect `_isRefreshing == true`, skip `_tryRefreshToken()`, and immediately return 401 session expired errors to the UI.

---

## Edge Cases

1. **Device Fingerprint Loss**: Clearing app data or reinstalling regenerates `_keyDeviceFingerprint` in `FlutterSecureStorage`. Subsequent API calls send a new `X-Device-Fingerprint`, triggering `AUTH_FAIL_006` ("Client binding mismatch") and forcing the user to log in again.
2. **IP Address Mobility**: Moving between cellular and Wi-Fi changes `req.ip`. Because `isIpRangeChanged()` only logs a security event rather than throwing an exception, user sessions remain active without disruption.
